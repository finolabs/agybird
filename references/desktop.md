# Desktop transport

Read this when the user chose the desktop transport (`/agybird:setup` or `$agybird-setup` reports `Transport: desktop`) or passes `--via desktop`. The CLI stays the default; nothing here applies to it.

## What it is

The runner `scripts/desktop.mjs` takes the same arguments, the same prompt on standard input and returns the same envelope as `scripts/agybird.mjs`, but the task runs in a new conversation of the Antigravity desktop app on macOS. It drives the app through the macOS Accessibility API: it sends no keystrokes, presses only the app's own controls and menu items, and touches no other app except to bring the user's front app back afterwards. The envelope carries `evidence.transport: "desktop"`, `evidence.app_version`, `evidence.preset` and `evidence.changed_files`.

```bash
command node "/absolute/path/to/agybird/scripts/desktop.mjs" \
  --category code \
  --cwd "/absolute/workspace" \
  --mode read <<'AGYBIRD_PROMPT_7F3A'
Explain how the parser handles empty input.
AGYBIRD_PROMPT_7F3A
```

Every run starts a new conversation; there is no resume. On 2.35 it opens from the project's own `New Conversation in Project` link in the sidebar. On 2.36 it opens from the one `New Conversation` link; then, unless the new conversation is already in the project, the runner opens its `Select project` picker, types nothing but sets the picker's `Search Projects` field to the project name, presses the item whose own name is exactly that name (never a near-name such as `agybird-wt-agy` for `agybird`) and reads the picker back. The new conversation must show `Where the agent runs, current: This Computer` before and after, so the working tree the run checks is the one the agent uses; any mismatch, a missing or second control, or another project read back ends the run `error` with nothing pasted or sent. The runner never changes where the agent runs, the branch, the model or the preset. The prompt's last line marks the run, `[agybird-run <16 hex digits>]`, drawn at random for each run; the line before asks the agent to ignore it, and it comes after any `--json-schema` instruction, so the reply contract is unchanged. The envelope returns it as `evidence.conversation_marker`. The runner pastes and presses Send only while the app shows the new, untitled conversation, and the same step that presses Send waits up to 30 seconds for the app to title it. That title identifies the run's conversation only when the same accessibility read shows, under that title, the run's own message with its marker (text of the conversation outside the agent's replies and, on 2.36, outside the sidebar drawn inside it), so neither a conversation that existed before nor one you create and send during the wait is adopted. From then on every read, Copy, Stop and answer requires the title and the marker in that same read. Antigravity 2.36 first titles a conversation with the prompt's first line and renames it a few seconds later; a poll that shows the run's own message, marker included, under a new title of the same project follows the rename and uses the new title from then on, and the evidence that frees a kept lock accepts the renamed conversation the same way. A Copy, Stop or answer pressed in the moment of a rename finds the old title and presses nothing. Every control the runner reads or presses (a permission dialog with its option 1, Skip and Submit, Copy among the reply's response actions, Stop execution, the reply, and whether a run is going) is taken only from inside that conversation's web area, the one titled web area whose text carries the marker. Before Send the new conversation has no marker yet, so the composer (`Message input`) the runner pastes into or clears and the `Send message` it presses are taken from the one titled web area showing the untitled new conversation ("Antigravity"), and each must be the only one of its kind in the whole app: a second composer or Send anywhere, an untitled pane's included, or one outside that web area ends the run `error` with nothing pasted, cleared or sent. When the app shows more than one titled conversation (a second window or pane), or such a control lies outside that web area, the run ends `error` with nothing pressed, and an approval refused that way stays approvable. The one exception is Copy, at the very end: the turn is over and the reply was already read, in the last poll, from the verified conversation alone, so a second pane that appears only then leaves Copy unpressed, and the run warns that the reply could not be copied and returns that on-screen reply instead (rendered text, without code fences), with the status it earns, `success` included. That the app renders its composer, Send, permission dialog, Stop button and Copy inside the conversation's web area, and shows one titled conversation at a time, has not been checked live: if it does not (a composer drawn outside the web area, say), runs fail closed this way until it is checked. Each read walks at most 20,000 accessibility nodes, and a read cut off there is never taken for the whole app, because a second conversation, composer or Send, the Stop button that shows the turn still running, or the rest of the reply may lie past the cut. Before Send such a read ends the run `error` with nothing pasted, cleared or sent, and an approval made on one presses nothing and stays approvable. After Send it never counts as a finished turn: the run keeps reading until its deadline, then presses Stop only from a whole read, and otherwise keeps the lock for the app and says the app may still be going, so it never returns `success` from a cut-off read. Nor is such a read evidence that frees a kept lock. A very large conversation or window therefore makes runs fail closed this way. A title that appears only later is never adopted. If you open another conversation in the app during a run, even before it is titled, or one with the same title, the run ends `error` without touching it, and so does a run whose own message the accessibility tree does not show (fail closed). On 2.36 the app shows a sent message collapsed behind `Expand message`, and its whole text, marker included, is one accessibility text (checked live); a message shown shortened, or left out of the tree, makes the run end `error` with nothing pressed. On 2.36 a turn shows `Cancel (⌃C)` instead of `Stop execution`, and Stop presses it; its reply spans several groups after `Agent said`, all read up to the response actions. The runner refuses `--category image`, `--swarm`, `--grant`, `--model`, `--effort`, `--agent`, `--sandbox` and `--conversation`, naming the flag: the app uses the model and settings chosen in it. Image work, usage and the review gate always use the CLI. `--json-schema` asks for one fenced JSON block at the end of the reply; the runner checks its top-level `required` keys and returns it as `structured_output`.

## Before a run

Grant Accessibility to the app that runs Agybird (the terminal, Claude, Codex or ZCode) in System Settings > Privacy & Security > Accessibility, then start a new session: a grant reaches only processes started after it. The workspace folder must already be a project in the app; the runner finds it in the project list the app shares with the CLI and opens a new conversation in it.

While the prompt is pasted (about a second), the app comes to the front and the clipboard holds the prompt, written on this Mac only and marked transient and concealed for clipboard managers; the clipboard is put back as soon as the paste reads back, the front app after Send, and the clipboard again right after the reply is copied (the app's Copy button writes the reply unmarked). Only the clipboard's text is put back: an image, a file or rich text on it is lost, and the run warns. Ask the user not to type into the app during that moment. If the pasted text reads back differently, the runner clears the input and sends nothing.

`blocked` names its reason in `evidence.blocked_reason`: `not_macos`, `app_missing` (open the app), `not_trusted` (grant Accessibility, new session), `unsupported_version` (outside the tested 2.35.x and 2.36.x; the user may confirm with `AGYBIRD_DESKTOP_ALLOW_VERSION=1`), `labels_missing` (another app version or language), `no_project` (open the folder as a project in the app), `ambiguous_project` (two projects share the name; rename one), `locked` (another desktop run is in progress, or an earlier one may still be going in the app).

## Permissions

The app's permissions preset is the user's own setting: the runner accepts `Request Review`, `Default`, `Auto` and `Turbo` and never changes it. Under `Auto` and `Turbo` the app may run commands and edit files without asking, and the envelope warns so. Read mode then only detects changes after the fact: any change to the working tree, or a moved `HEAD`, makes the run `error`, and `changed_files` names the files. Files git ignores are not compared. In write mode `diff_stat` adds the added and removed lines of each changed file, against `HEAD`.

When the app asks for a permission, the run ends `needs_permission` with the app still waiting. Each request carries the app's whole `question` (read from every text of the dialog), the rule `scope` its wider options name, and the `options` shown. Put the question in front of the user. A question longer than 4,000 characters is shortened, `question_truncated` is set and `approvable` is false: it can only be answered in the app. Approving answers "Yes, allow this time" once: `companion.mjs task --approve <job-id>:<n>` with no other flag. In the same read that presses it, the runner checks that the app shows the conversation that asked (its title and the asking run's own message with its marker), the same whole question and that exact option, all inside the one dialog it presses, and refuses otherwise, also when two dialogs on screen ask the same question. If the run had already changed the working tree in read mode, the runner declines the prompt and the run ends `error` instead. Each request is answered once; it counts as answered from the moment the runner starts to press the answer, so only an approval whose run stopped before that (another desktop run held the app, for example), or whose answer the app refused before any press (another conversation or question on screen, a changed option 1), can be given again. When the answer's own step fails in a way that may come after the press (a timeout, a crash, a failed press, a cancel during it), the runner treats it as pressed, like an uncertain Send: it presses Stop in that conversation or keeps the lock for the app, sets `evidence.answer_uncertain`, and the request counts as answered. The runner records the answer in the job store (`<job>.answered-<n>`) before it starts to press it, and removes the record only when the app refused the answer before any press, so an approval interrupted at any point from then on (Ctrl+C, the host's timeout, or a kill, during the press included) is spent; a record already there stops the run before anything is pressed; an interrupted foreground approval also waits for the runner to finish and records its result before it exits. When the user declines, `companion.mjs task --decline <job-id>:<n>` answers Skip in the app with the same checks, so the agent hears the refusal instead of waiting. Agybird never presses the options that allow a command for the whole conversation or always; when the user wants that, they answer in the app themselves. A run that reaches its deadline is stopped in the app, and so is one that is cancelled, interrupted (Ctrl+C or the host's own timeout gives it the same 20 seconds as a cancel, more than its cleanup's bounded app calls can take) or that fails after Send; a cancel cuts short the step in flight, a long paste included, and clears a prompt pasted but not sent, also when it lands while the clipboard is put back just before Send: Send is then not pressed, no Stop is pressed and the lock is released. From just before it presses Send or an answer, the run marks `desktop.lock` as kept for the app, with the conversation's title once known and the run's marker, so the lock survives the run however it ends. When Stop cannot be pressed in the run's own conversation, the run says the app may still be going and leaves that lock in place. It never expires on time alone: a later run is admitted only once it finds the app showing that conversation (its title and its run's marker) with no run, and otherwise ends `blocked` with reason `locked`, naming the conversation and the lock's path, which the user may remove once the app runs nothing for it.
